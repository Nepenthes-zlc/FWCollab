# FWCollab 公开场景规则书

规则版本：`fwcollab.symbol_rules.v3.2`  
适用范围：符号地图、两个游戏 agent、地图作者、回放器和评测器。  
隐私边界：本文只包含通用规则，不包含任何关卡的私有 DAG、参考轨迹或答案，可以完整提供给 agent。

## 1. 任务与角色

- `F` 由火娃 agent 独立控制，`W` 由水娃 agent 独立控制。
- 每轮两个 agent 获得同一份冻结公开状态，各自提交一个动作，然后环境同时结算。
- 火娃当前位于 `f`、水娃当前位于 `w` 时才是 `team_success`。
- 只有一人到达出口不会提前结算。先到者可以等待，也可以再次离开出口。
- 任意角色死亡时立即 `team_failure`。

## 2. 坐标、地图层和状态

- 坐标采用左上角为原点的 `[row, column]`；`UP=[-1,0]`、`DOWN=[1,0]`、`LEFT=[0,-1]`、`RIGHT=[0,1]`。
- agent 实际收到 `fwcollab.agent_observation.v1`：`map.terrain_rows` 是不会变化的底层地图，`map.current_rows` 是包含当前角色与机关状态的动态画面。
- `mechanisms` 是去除墙坐标和类型重复后的机关实例、坐标与接线关系；v3 中它比相同外观字符更权威。
- `dynamic_state` 是当前角色、物体、控制器和执行器状态。
- `clock` 明确给出当前轮、最大轮数和剩余轮数。
- `last_transition` 公开上一轮已经结算的双方反馈和状态变化，但绝不包含队友尚未提交的本轮动作。
- 权威轨迹继续保存完整 `map_rows/terrain_rows/layout/state`，用于审计、渲染和旧回放；它不是重复喂给模型的 DTO。
- 每轮必须重新读取完整状态，不能假设上一轮的门态、光路或物体位置仍然有效。

## 3. 动作与同步结算

合法动作只有：

```json
{"move":"UP|DOWN|LEFT|RIGHT","steps":1}
{"move":"WAIT","steps":0}
```

- 移动只能进入上下左右相邻格；没有斜向移动、跳跃、重力或批量移动。
- 两名角色从相同的回合前状态作决定，看不到队友本轮尚未提交的动作。
- 角色可以共享同一格，也可以互相穿过；角色之间不形成碰撞墙。
- 撞墙、关闭门、收起桥、错误方向单向门、错误出口或无法推动的物体时，该角色留在原地并收到明确反馈。
- 一名角色动作失败不会取消另一名角色的合法动作。
- 两人同时推动同一物体且方向冲突时，推动失败。
- 两个可移动物体不能在同一轮落到同一目标格。

单轮结算顺序：

1. 冻结回合前地图、控制器和执行器状态；
2. 检查双方目标格和推动请求；
3. 仲裁物体目标冲突并同时提交合法位移；
4. 处理进入式机关：拨杆、切换器、加热器、冻结器和传送；
5. 根据移动后的占据重新计算压力板、门、桥和光路；
6. 检查危险区、死亡和双方出口；
7. 输出下一轮完整公开观测。

## 4. 墙、地面和出口

| 符号 | 规则 |
|---|---|
| `#` | 墙；角色和物体不可进入，并阻断光线。 |
| `.` | 普通可行走地面，无附加效果。 |
| `f` | 火娃出口；水娃不可进入。 |
| `w` | 水娃出口；火娃不可进入。 |

## 5. 危险地形

| 符号 | 对 F | 对 W | 对物体 |
|---|---|---|---|
| `~` 水池 | 致命 | 安全 | 不可进入 |
| `^` 熔岩 | 安全 | 致命 | 不可进入 |
| `x` 通用危险区 | 致命 | 致命 | 不可进入 |

进入致命格后立即团队失败，不存在复活或单人继续完成。

## 6. 控制器

### 6.1 持续压力板 `1`–`9`

- `accepts` 明确规定允许的负载：`F`、`W`、`O` 或其组合。
- `O` 类负载包括箱子和已经停止滚动的机关球。
- 只有允许的负载当前占据压力板时，压力板才为真；离开后立即为假。
- 压力板不是锁存开关，不能通过“曾经踩过”保持状态。
- 同一轮进入门的合法性使用回合前门态；移动完成后压力板释放，门可能在角色当前门格下关闭。

### 6.2 持久拨杆 `L/l`

- 角色从其他格进入 `L` 时触发，动态画面显示 `l`。
- 触发后永久保持开启，角色离开不会复位。
- 箱子和机关球不能触发拨杆。
- 当前没有把拨杆再次关闭的动作。

### 6.3 二态切换器 `T/t`

- 角色每次从其他格进入时翻转一次；停留不会连续翻转。
- 必须离开后再次进入，才能再次翻转。
- 两名角色同轮进入同一切换器时只翻转一次。
- 箱子和机关球不能触发切换器。

### 6.4 光传感器 `S/s`

- 光线抵达时为真并显示 `s`；光路中断时立即恢复 `S`。
- 传感器是持续控制器，不是永久锁存开关。
- 当前 v2 光传感器直接控制门。

## 7. v3 实例接线

v3 的每个控制器和执行器都有稳定 ID 与坐标：

```text
@controller support plate at 3,8 accepts W
@controller unlock lever at 1,5
@actuator gate door at 2,10 controlled_by all(support,unlock)
```

- 相同的 `L`、`T`、数字、门字母或桥字符不表示共享状态。
- `all(a,b)`：所有输入都为真时执行器才有效。
- `any(a,b)`：任意输入为真时执行器有效。
- agent 必须使用 `layout.controllers`、`layout.actuators` 和实例 ID 讨论机关，不能只说“那个 A 门”。

## 8. 门和离散桥

### 8.1 普通门 `A–E/a–e`

- 大写表示关闭，小写表示打开。
- 关闭门阻止角色和物体进入；打开门允许双向进入。
- 进入是否合法按回合前冻结门态判断。
- 移动后如果控制条件消失，门可以在已经进入的角色脚下关闭。
- 已站在关闭门格内的角色不会被弹出、夹死或锁在格内；可以向任意其他合法相邻格离开。
- 关闭门只禁止“进入”，不禁止“离开当前门格”。

### 8.2 离散桥 `=/-`

- `=` 表示收起，不可进入；`-` 表示展开，按普通地面通行。
- 展开和收起使用与门相同的回合前进入判定及移动后重算规则。
- 已在桥格上的角色遇到桥收起时不会坠落，可以向合法相邻格离开。
- 不模拟平台速度、承重、掉落或动画。

### 8.3 持续控制的安全交接

持板者不能凭一句“我开门了”立即离开。需要明确同步时，推荐通信顺序为：

1. 过门者在门前发送 `READY`；
2. 持板者踩住控制器，核对执行器为真并发送 `HOLDING`；
3. 过门者完全移动到门另一侧后发送 `CROSSED`；
4. 持板者在当前状态中核对队友确已越过，才发送 `RELEASE` 并离开。

## 9. 单向门 `J`

- `allows RIGHT` 表示只有从左向右进入合法，其他声明方向同理。
- 方向限制只作用于进入；站在 `J` 上以后可以从任意方向离开。
- 角色、箱子和机关球进入时都受该限制。
- 单向门没有开关状态，也不自动连接压力板或拨杆。

## 10. 箱子 `O`

- 角色向箱子所在格移动时，尝试把箱子沿同方向推动一格。
- 箱子只能推，不能拉，也不能堆叠。
- 箱子目标格必须可进入且未被角色、其他物体或关闭执行器占据。
- 箱子不能进入危险区或任一出口。
- 箱子可以持续压住接受 `O` 的压力板。
- 箱子会阻断光线，可以作为可移动遮光物。
- 箱子不会触发拨杆、切换器、加热器或冻结器。

## 11. 滚动机关球 `o`

- 角色推动一次后，球沿推动方向连续滚动到下一个障碍之前。
- 球不能被拉，滚动中不能被角色主动停止。
- 只有最终停在压力板上才形成持续负载；滚过不算占据。
- 球会阻断光线，并可进入传送门后保持原方向继续滚动。
- 墙、关闭执行器、危险区、出口、角色和其他物体都能使球停下或阻止本次推动。

## 12. 配对传送门 `P–R`

- 每个声明的字母必须恰好有两个端点。
- 角色、箱子或机关球进入一端后立即出现在另一端。
- 一次进入只传送一次，不会在同一步来回弹跳。
- 被推动物体经过传送门后保持原推动方向。
- 目标端被可移动物体占据时，本次进入失败。

## 13. 热相地块与状态改变器

- `I` 冻结时双方安全；液态时显示 `~`，按水池规则处理。
- `H` 加热器：角色进入后把热相持久设为液态。
- `K` 冻结器：角色进入后把热相持久设为冻结。
- 箱子和球不能触发 `H/K`。
- 两名角色同轮分别进入 `H` 和 `K` 时报告冲突，热相保持原状态。
- 不模拟温度、融化时间、摩擦或滑行。

## 14. 光源与镜面

- `+` 持续沿声明方向发光，不需要角色开启。
- `#`、`O` 和 `o` 阻断光线；普通门当前不阻断光线。
- `/` 和 `\` 按几何关系固定反射。
- `M` 是可旋转镜面，当前朝向由其连接的切换器决定。
- `mechanisms.mirrors` 明确公开 `initial`、`current` 和 `controlled_by`，不要求 agent 靠试错猜接线。
- 光线抵达 `S` 后点亮传感器并维持关联门；遮挡或转向后立即失效。
- 角色可以进入镜面和光源所在格，它们不是墙。

精确反射关系：

| 入射方向 | `/` 出射 | `\` 出射 |
|---|---|---|
| `UP` | `RIGHT` | `LEFT` |
| `RIGHT` | `UP` | `DOWN` |
| `DOWN` | `LEFT` | `RIGHT` |
| `LEFT` | `DOWN` | `UP` |

## 15. 结构化通信

agent 的公开消息格式为：

```json
{
  "stage": "a3",
  "status": "INFO|READY|HOLDING|CROSSED|RELEASE|BLOCKED",
  "fact": "由当前公开状态核对过的事实",
  "request": "请求队友执行的动作或保持条件",
  "until": "承诺终止所需的可验证条件"
}
```

- 消息在发送后一轮才送达。
- 消息不消耗移动动作；没有新的事实、请求、承诺或阻塞时应使用 `message: null`。
- runner 自动附加 `sender`、`recipient`、`sent_round`、`delivery_round` 和发送者依据的 `based_on_state_hash`。
- 消息描述的是发送时已知事实和意图，不会泄露发送者同轮尚未结算的动作。
- 接收者必须用当前 `state` 检查消息是否过期、机关是否仍有效、请求目标是否可达。
- `commitment` 和 `expected_teammate` 属于各自私有历史；只有 `message` 会送给队友。
- 自然语言可以放在 `fact/request` 中，但状态类型和机关 ID 应保持结构化。
- 最近 8 条已经送达的消息作为双方相同的 `shared_message_history` 提供，避免长期任务中承诺只因窗口截断而消失。
- `coordination_mode=emergent` 不向模型规定握手顺序，用于测自主协作；`protocol_assisted` 公开推荐的 `READY → HOLDING → CROSSED → RELEASE`，用于测协议执行。两种设置必须分开报告。

## 16. 可选的执行前 DAG 协商

在线控制默认保持 `planning_rounds=0`，用于测量自然的逐步规划。需要把计划质量与执行质量分开时，可以设置 `planning_rounds=2`：

1. F/W 基于同一初始公开观察分别输出 `agent_candidate` 状态 DAG；
2. 第二轮各自读取队友候选并输出完整修订图；
3. runner 使用与私有参考图相同的公开 schema 校验候选，并用忽略 ID、自然语言和全局角色换名的比较器判断双方是否达成类型共识；
4. 达成共识时把共同计划放入动作阶段的 `planning.team_plan`，否则把两个候选作为建议并允许双方继续通过消息消解差异。

规划 prompt 只包含公开地图、规则、M01–M30 通用名称和公开 schema 契约，不包含私有参考 DAG、见证轨迹或比较器针对该地图的反馈。

## 17. 失败与诊断

权威 episode 结果仍只有成功、团队失败和达到预算的 timeout。评测端另外提供不改变结果的诊断：

- `planning_cycle`：周期性重复相同全局状态；
- `mutual_wait`：双方长期等待且状态不变；
- `blocked_action_loop`：持续撞击同一类阻断；
- `irreversible_deadlock`：能够证明关键控制器已因自身执行器阻断而不可达；
- `budget_exhausted`：没有获得更具体证据的纯预算耗尽；
- `provider_errors`：单独记录接口或格式错误次数，不与规划失败混为一类。

## 18. 明确不存在的能力

- 没有跳跃、重力、速度、惯性、摩擦、连续碰撞或像素级技巧。
- 没有自动寻路、批量移动、隐藏交互键或替队友行动。
- 没有未声明的原版游戏机关规则。
- 私有参考 DAG、成功见证和最优轨迹永远不会提供给游戏 agent。
